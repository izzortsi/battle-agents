## A1. Synchronous Dialogue Protocol

### The Problem

When agent $a$ emits `CHAT(target=b, message=m)$, agent $b$ needs to respond *within the same game tick*. This creates a mini-dialogue that must be:

- **Bounded** in length (we can't let two agents chat forever)
- **Observable** by nearby agents (who store the exchange in their own memories)
- **Narratively natural** (not just single-line pings)
- **Cost-controlled** (each exchange round costs an LLM call per participant)

### Protocol: Bounded Synchronous Exchange

A `CHAT` action triggers a **dialogue session** of at most $L_{\max}$ exchange rounds (default $L_{\max} = 3$). The protocol is:

```
Agent a decides CHAT(target=b, message=m₁)
  │
  ▼
DialogueSession opens between a and b
  │
  ├── Round 1:  a says m₁
  │             b receives m₁, generates response m₂ (+ continue/end flag)
  │
  ├── Round 2:  a receives m₂, generates m₃ (+ continue/end flag)
  │             b receives m₃, generates m₄ (+ continue/end flag)
  │
  ├── Round 3:  [if both still continuing]
  │             a generates m₅, b generates m₆
  │
  └── Session closes (max rounds reached or either party signals end)
```

Each response is generated by a single LLM call with the dialogue history so far. The prompt includes:

- The responder's identity, personality, and current goals
- Retrieved memories about the initiator (via retrieval function)
- The conversation so far
- Instruction to produce: `{"message": "...", "continue": true/false, "disposition_shift": float}`

The `disposition_shift` is the responder's own self-reported internal reaction (e.g., $+0.1$ if the conversation was pleasant, $-0.2$ if threatened). This feeds into the social model.

### LLM Call Budget

For $L_{\max} = 3$: worst case is 6 LLM calls per dialogue (3 per participant). In practice, most exchanges end at round 2 (the responder says something, the initiator wraps up), costing 3-4 calls.

### Memory Emission

After a dialogue session closes:

1. The full exchange is summarized into **one `MemoryNode`** per participant, e.g.:
   - For $a$: *"Kael proposed an alliance with Lyra against Vorn. Lyra was cautious but agreed to a temporary truce."*
   - For $b$: *"Kael approached Lyra proposing a joint attack on Vorn. Lyra agreed to a truce but remains wary of Kael's true motives."*
   
   Note the asymmetry — each agent summarizes from their own perspective. This is generated by a cheap LLM call or a template.

2. Nearby agents (within perception radius but not participants) receive an **overheard observation**: *"Kael and Lyra were seen talking intensely near the east wall."* — they get the fact of the conversation but not its content, unless they were close enough (configurable).

### Dialogue During Combat vs Pre-Battle

| Phase | Chat cost | $L_{\max}$ | Notes |
|-------|-----------|------------|-------|
| Pre-battle | Free action (no turn cost) | 4 | Social phase, conversation is the point |
| Combat | Costs the agent's action for the turn | 2 | Shorter, higher stakes — you're burning a combat action |

During combat, the initiator sacrifices their action to start a dialogue, but the responder does *not* — they respond "for free" as an interrupt. This asymmetry matters: the initiator pays a real tactical cost to attempt negotiation.

### Module

```
cognition/
└── dialogue.py    # DialogueSession, exchange loop, summary generation
```

### Data Flow


## A2. Dynamic Alliance System

### Core Idea

Alliances are **not a game mechanic** — they are an **emergent property** of the social model. There is no "form alliance" button. Instead, alliances emerge from:

1. Conversations where agents agree to cooperate
2. Consistent non-hostile behavior toward each other
3. Shared enemies or threats

The environment controller *infers* alliance status from the social model for purposes like friendly fire prevention and victory conditions.

### Alliance State Machine

From the agent's perspective, each relationship has a `disposition` in $[-1, 1]$. The environment controller maps this to alliance status:

$$
\text{alliance\_status}(a, b) = \begin{cases}
\texttt{ALLIED} & \text{if } d_a(b) > \tau_+ \;\text{and}\; d_b(a) > \tau_+ \\
\texttt{HOSTILE} & \text{if } d_a(b) < \tau_- \;\text{or}\; d_b(a) < \tau_- \\
\texttt{NEUTRAL} & \text{otherwise}
\end{cases}
$$

where $d_a(b)$ is agent $a$'s disposition toward $b$, and $\tau_+ = 0.5$, $\tau_- = -0.3$ by default.

**Crucially, alliance is mutual for `ALLIED` but unilateral for `HOSTILE`.** If $a$ hates $b$ but $b$ likes $a$, the status is `HOSTILE` — $a$ will attack, and $b$ will be surprised. This asymmetry is exactly the kind of dramatic emergence we want.

### Friendly Fire Rules

| Alliance status | Attack allowed? | Consequence |
|-----------------|----------------|-------------|
| `ALLIED` | Yes, but penalized | Massive disposition drop, alliance breaks |
| `NEUTRAL` | Yes | Normal disposition shift |
| `HOSTILE` | Yes | No additional penalty |

Agents *can* always attack anyone — the system never hard-blocks. But attacking an ally causes such a large disposition collapse that it effectively functions as betrayal. The LLM-driven agent cognition will naturally avoid this unless the agent has a deliberate reason (backstory rivalry, strategic calculation, etc.).

### Victory Conditions with Dynamic Alliances

- **Free-for-all (default)**: last individual standing wins. Alliances are tactical but ultimately temporary.
- **Team mode**: at battle start, a "team check" freezes current alliances into teams. Teams win together. Agents *within* a team can still betray (breaking the team), but the victory condition encourages cooperation.
- **Last-faction-standing**: like free-for-all, but if all surviving agents are `ALLIED` with each other, they win collectively.

### Disposition Update Rules

Disposition evolves through multiple channels:

| Event | $\Delta d$ | Channel |
|-------|-----------|---------|
| Agent $b$ attacks $a$ | $-0.3$ to $-0.5$ | Heuristic |
| Agent $b$ heals/buffs $a$ | $+0.2$ to $+0.4$ | Heuristic |
| Agent $b$ kills $a$'s ally | $-0.2$ | Heuristic |
| Agent $b$ kills $a$'s enemy | $+0.15$ | Heuristic |
| Positive dialogue outcome | $+0.05$ to $+0.2$ | Dialogue self-report |
| Threatening dialogue | $-0.1$ to $-0.2$ | Dialogue self-report |
| Reflection reappraisal | Variable | LLM-driven (during reflection) |

The heuristic channel fires immediately. The LLM reappraisal fires during reflection and can *override* heuristic shifts with nuanced reasoning (e.g., "they attacked me, but I think it was accidental — they were aiming at someone behind me").

## A3. Bundled Embedding Model

### Decision

Bundle `nomic-embed-text` (768-dim, ~275M params) as the default embedding model. It runs efficiently on CPU and is available through ollama.

### Architecture

```
llm/
└── embeddings.py
    ├── EmbeddingProvider (ABC)
    ├── OllamaEmbeddings       # ollama pull nomic-embed-text
    ├── AnthropicEmbeddings    # via voyage-3-lite (Anthropic's recommended)
    ├── OpenAIEmbeddings       # text-embedding-3-small
    └── EmbeddingCache         # LRU cache to avoid re-embedding known strings
```

### Usage in Retrieval

The retrieval function's relevance component now always uses embeddings:

$$
\text{relevance}(m, q) = \text{cosine\_sim}\bigl(\text{embed}(m.\text{description}),\; \text{embed}(q)\bigr)
$$

where $q$ is the query string constructed from the current tactical situation.

### Embedding Cache

Memories are embedded once at creation time and cached. The query embedding is computed per retrieval call. With ~100 memories per agent and 4-6 agents, the cache holds ~600 vectors — trivial memory footprint.

```python
class EmbeddingCache:
    """LRU cache mapping text → embedding vector."""
    
    def __init__(self, provider: EmbeddingProvider, max_size: int = 2048):
        self._provider = provider
        self._cache: OrderedDict[str, List[float]] = OrderedDict()
        self._max_size = max_size
    
    def embed(self, text: str) -> List[float]:
        if text in self._cache:
            self._cache.move_to_end(text)
            return self._cache[text]
        vec = self._provider.embed([text])[0]
        self._cache[text] = vec
        if len(self._cache) > self._max_size:
            self._cache.popitem(last=False)
        return vec
```

### Fallback

If no embedding model is available at all (edge case), fall back to keyword overlap — same as the existing codebase's approach. The retrieval function auto-detects:

```python
def compute_relevance(memory: MemoryNode, query: str, embedder: Optional[EmbeddingCache]) -> float:
    if embedder is not None:
        return cosine_sim(embedder.embed(memory.description), embedder.embed(query))
    else:
        return keyword_overlap(memory.keywords, extract_keywords(query))
```

## A4. Pre-Battle Social Phase — Duration Analysis

### Suggested Duration: 6 ticks

Your instinct of 4 is reasonable, but I think 6 is the sweet spot. Here's the analysis.

### What Needs to Happen

For the pre-battle phase to produce meaningful social structure, each agent should:

1. **Perceive** most other agents (at least those nearby)
2. **Converse** with 2-3 other agents (enough to form 1-2 opinions)
3. **Establish** at least one alliance or enmity beyond initial backstory seeds
4. **Diffuse information** — agent $a$ tells $b$ something about $c$, and $b$ acts on it

### Tick-by-Tick Model (5 agents)

The pre-battle phase uses **simultaneous ticks** (all agents act in parallel), not sequential turns. Each tick, every agent runs a simplified cognitive loop: perceive → retrieve → decide (chat / move / observe).

| Tick | Expected Activity | Social Graph Effect |
|------|-------------------|---------------------|
| 1 | Agents spawn in staging area, perceive nearby agents, form initial observations from backstory | Graph: isolated nodes with backstory edges |
| 2 | First conversations begin (1-2 dialogues). Agents with pre-existing relationships seek each other out | Graph: 2-3 edges added |
| 3 | More conversations. Agents who overheard others talking may approach. First alliance proposals possible | Graph: 4-5 edges, first clusters forming |
| 4 | Information diffusion: "Did you hear what Kael said about Vorn?" Second-order social dynamics | Graph: 6+ edges, information spreading |
| 5 | Alliances solidify or tensions escalate. Agents may reposition socially based on what they've learned | Graph: alliance/hostility structure stabilizing |
| 6 | Last interactions. Agents finalize their plans for the upcoming battle. Reflection may trigger (importance accumulates from 5 ticks of social activity) | Graph: ready for combat |

### LLM Call Budget (6 ticks, 5 agents)

Per tick:
- 5 agents × 1 decision call = 5 calls
- ~2 dialogues × ~4 calls each = 8 calls  
- ~2 dialogue summaries = 2 calls (cheap model)
- Total: ~15 calls per tick

Over 6 ticks: ~90 calls. At ~$0.002/call with Haiku-class models, that's ~$0.18. Acceptable.

### Why Not 4?

With 4 ticks, each agent gets ~1.5 conversations. That's enough to form one relationship but not enough for:
- Information diffusion (A→B→C needs at least 2 conversation rounds)
- Reflection triggering (unlikely to accumulate enough importance in 4 ticks)
- The "social surprise" moments (overhearing something, changing plans)

### Why Not 8+?

Diminishing returns. By tick 6, the social graph is well-formed. Additional ticks mostly produce redundant conversations. Also, the player/observer wants to see combat — the pre-battle is appetizer, not entree.

### Configuration

Make it a `game_config.yaml` parameter with default 6:

```yaml
pre_battle:
  enabled: true
  duration_ticks: 6          # configurable, suggested range [4, 8]
  tick_mode: simultaneous     # all agents act in parallel
  chat_max_rounds: 4          # longer conversations in social phase
  perception_radius: 12       # larger than combat radius — it's a social space
```

## A5. Scalability Architecture (4–6 now, 10+ later)

### Current Target: 4–6 Agents

At this scale, sequential processing is fine. Each combat turn:
- 6 agents × 1 decision call ≈ 6 LLM calls (parallelizable)
- ~1 dialogue session ≈ 4 calls
- ~0.5 reflections ≈ 1 call
- Total: ~11 calls/turn, ~2-4 seconds with parallel API calls

### Scaling to 10+: Design-for-Scale Patterns

Even though we're building for 4-6, these patterns cost almost nothing to implement now and save major refactoring later:

**Pattern 1: Agent-level parallelism.**  
Each agent's cognitive loop is independent (they read shared state but write to their own memory). Wrap each agent's turn in a `concurrent.futures` task.

```python
# In cognitive_loop.py
async def run_all_agents(agents: List[Agent], env: Environment) -> Dict[str, Action]:
    tasks = {
        agent.name: asyncio.create_task(run_single_agent(agent, env))
        for agent in agents if agent.is_alive()
    }
    results = await asyncio.gather(*tasks.values())
    return dict(zip(tasks.keys(), results))
```

**Pattern 2: Model routing by agent importance.**  
Not all agents need the same model quality. The "main characters" (lowest HP, most active in dialogue) get the strong model; background agents get a cheaper one.

```python
def select_model(agent: Agent, router: ModelRouter) -> LLMAdapter:
    if agent.scratch.hp / agent.scratch.max_hp < 0.3:
        return router.get("strong")   # critical decisions deserve better reasoning
    if agent.recent_dialogue_count > 2:
        return router.get("strong")   # socially active agents need nuance
    return router.get("cheap")
```

**Pattern 3: Perception culling.**  
At 10+ agents, building the full battlefield description for every agent is wasteful. Only include agents within perception radius + 2 tiles.

**Pattern 4: Batched embedding.**  
Embed all new memories across all agents in a single batch call, rather than one-by-one.

### Data Structure Scalability

The `WorldState` (ontology layer) uses dictionaries keyed by entity ID — $O(1)$ lookups, scales linearly with entity count. The `AssociativeMemory` per agent grows linearly with turns, but retrieval is $O(n)$ over all nodes — at 100+ turns with 10+ agents, this might need an index. A simple fix: pre-filter by `MemoryType` and recency before scoring.

## A6. Campaign Mode vs Run-Once

### Two Modes

```yaml
# game_config.yaml
mode: "campaign"   # or "run_once"

campaign:
  battle_count: 5
  memory_carry: true
  memory_compression: true       # compress old memories between battles
  xp_progression: true            # agents gain stats between battles
  roster_persistent: true         # same agents across battles
```

### Run-Once Mode

Simple: load characters, run pre-battle + combat, serialize final state, done. Memory exists only within the single battle. This is the default for testing and one-off spectacles.

### Campaign Mode

After each battle:

1. **Memory Compression**: the full memory stream is too large to carry indefinitely. Between battles, run a compression pass:
   - Keep all reflections (they're already high-level summaries)
   - Keep the top-K most important observations (by poignancy)
   - Summarize the rest into 3-5 "campaign memories" via an LLM call:
     *"In the previous battle, Kael defeated Lyra but was gravely wounded by Vorn's surprise attack. Kael and Mira fought as allies throughout."*
   - Discard the raw observations

   This mirrors how human memory works: specific vivid moments survive, but the bulk fades into generalized impressions.

2. **Social Model Persistence**: dispositions, trust, betrayal counts carry over directly. An agent who was betrayed in battle 1 remembers it in battle 3.

3. **XP/Stat Progression** (optional): winners gain small stat boosts or new abilities. Losers (eliminated agents) can return in the next battle with a "grudge" backstory addition.

4. **Roster Management**: agents persist across battles. New agents can join; eliminated agents can be resurrected or permanently retired.

### Campaign State Serialization

```python
@dataclass
class CampaignState:
    campaign_id: str
    battle_number: int
    roster: List[AgentSnapshot]          # identity + current stats + social model
    compressed_memories: Dict[str, List[MemoryNode]]   # per agent
    battle_history: List[BattleResult]   # outcomes of previous battles
    
    def save(self, path: str): ...
    
    @classmethod
    def load(cls, path: str) -> "CampaignState": ...

@dataclass
class BattleResult:
    battle_number: int
    winner: Optional[str]
    survivors: List[str]
    eliminated: List[str]
    turn_count: int
    summary: str           # LLM-generated narrative summary
```

### Memory Compression Algorithm

Between battles, for each agent:

```python
def compress_memories(memory: MemoryStream, keep_top_k: int = 20) -> MemoryStream:
    reflections = memory.get_by_type(REFLECTION)      # keep all
    plans = []                                          # discard (stale)
    
    observations = memory.get_by_type(OBSERVATION)
    observations.sort(key=lambda m: m.poignancy, reverse=True)
    top_observations = observations[:keep_top_k]        # keep vivid moments
    
    remaining = observations[keep_top_k:]
    if remaining:
        # Summarize the rest into campaign memories
        summaries = llm_summarize_memories(remaining, max_summaries=3)
        campaign_nodes = [
            MemoryNode(type=REFLECTION, depth=2, description=s, poignancy=7)
            for s in summaries
        ]
    else:
        campaign_nodes = []
    
    compressed = MemoryStream()
    for node in reflections + top_observations + campaign_nodes:
        compressed.add(node)
    return compressed
```

The `depth=2` on campaign summaries marks them as meta-reflections — reflections built on top of reflections. This extends Park et al.'s reflection tree across battle boundaries.

## A8. Updated Implementation Roadmap

With the resolved decisions, the phasing becomes:

### Phase 1: Ontology + World + Agent Shell *(no LLM)*

Build the data backbone. At the end of this phase, you can place agents on a grid, tick the world forward with random actions, and inspect the world state / agent knowledge.

Modules: `ontology/`, `world/`, `agent/`, `combat/actions.py`, `combat/action_resolver.py`

### Phase 2: Memory + Retrieval + Embeddings + Basic Decision

Wire up the cognitive core. Agents make LLM-driven decisions informed by their memory stream.

Modules: `llm/adapter.py` + adapters, `cognition/memory_stream.py`, `cognition/retrieval.py`, `cognition/embeddings.py`, `cognition/decision.py`, `cognition/cognitive_loop.py`

### Phase 3: Dialogue + Social Model + Reflection + Planning

This is where emergence starts. Agents talk, form alliances, reflect on experiences, and plan.

Modules: `cognition/dialogue.py`, `cognition/reflection.py`, `cognition/planner.py`, `agent/social_model.py`, `world/alliance_resolver.py`

### Phase 4: Pre-Battle Phase + Game Flow

The full two-phase simulation: social → combat. End-to-end playable.

Modules: `world/turn_manager.py` (pre-battle mode), game flow orchestration in `runner.py`

### Phase 5: Campaign Mode

Persistence across battles: memory compression, state serialization, stat progression.

Modules: `campaign/`

### Phase 6: Frontend + Polish

Phaser.js visualization, UI panels, replay system.

Modules: `frontend/`
