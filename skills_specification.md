## The Skills System — Complete Summary

### What It Is

A data-driven ability and status effect system for an LLM-powered tactical battle arena. Characters are generated by LLMs with unique abilities, each carrying themed status effects that are automatically registered into a persistent registry and mechanically enforced during combat — all without code changes for novel effect types.

---

### 1. Ability Data Model

Abilities are `List[Dict[str, Any]]` on `CombatScratch` — **not** typed dataclasses. This is deliberate: LLM-generated characters can produce novel ability structures that pass through serialization without schema changes.

**Required fields:** `name`, `mana_cost`, `damage`, `range`, `aoe_pattern`, `cooldown`, `current_cd`

**Enrichment fields:** `description` (what it does narratively), `tactical_hint` (when/why to use it), `effects` (list of effect dicts)

All fields accessed via `.get()` with defaults — old characters missing enrichment fields degrade gracefully.

The `Ability` dataclass in `actions.py` exists only as a transient container inside `CombatAction` for the resolver. The source of truth is always the dict on scratch.

---

### 2. Effect Schema

Each effect on an ability is a dict:

| Field | Type | Purpose |
|-------|------|---------|
| `type` | str | The effect name — can be anything ("burn", "searing_entangle", "heat_haze") |
| `behavior` | str | Mechanical enforcement category — one of 9 valid behaviors |
| `duration` | int | Turns the effect persists |
| `magnitude` | float 0–1 | Strength — meaning varies by behavior |
| `target` | "self" \| "enemy" | Who receives the effect |
| `category` | "buff" \| "debuff" \| "movement" \| "heal" | Dispatch category for the resolver |
| `chance` | float 0–1 | Probability of application (1.0 for buffs, 0.6–0.85 for debuffs) |

---

### 3. The Status Registry

**Location:** `backend/combat/statuses/`

**Core idea:** Every status type maps to a **behavior** — a mechanical category determining what happens at runtime. Nine behaviors exist; unlimited type names can map to them.

**The nine behaviors:**

| Behavior | What It Does | Enforced In |
|----------|-------------|-------------|
| `miss_chance` | Attacks/abilities may miss (magnitude = miss probability) | action_resolver ATTACK + ABILITY |
| `skip_turn` | Lose entire turn | battle_server process_turn |
| `prevent_move` | Cannot move; reduces initiative speed | action_resolver MOVE; battle_server initiative |
| `damage_over_time` | Takes magnitude × max_hp damage per round | battle_server end-of-round |
| `reduce_outgoing_damage` | Outgoing damage × (1 - magnitude) | action_resolver _apply_damage |
| `boost_outgoing_damage` | Outgoing damage × (1 + magnitude) | action_resolver _apply_damage |
| `reduce_incoming_damage` | Incoming damage × (1 - magnitude) | action_resolver _apply_damage |
| `stat_modifier` | Boosts initiative speed; +1 movement range | battle_server, action_resolver, agent_brain |
| `passive` | Tracked and displayed but no automatic enforcement | — |

**Lookup chain** (`get_behavior(type_name)`):
1. Check registry for a loaded definition → return its `behavior` field
2. Attempt keyword inference from the type name (e.g., "burning" contains "burn" → `damage_over_time`)
3. Fall back to `"passive"`

**Definition files:** JSON files in `definitions/` — 9 hand-authored base types (blind, stun, poison, slow, defend, weaken, empower, haste, shield) plus any auto-generated novel types.

---

### 4. Character Generation — Where Abilities Are Born

**Two-layer LLM process** (`character_generator.py`):

- **Layer 1:** Narrative identity — personality, backstory, class, weapon/armor/accessory, fighting style
- **Layer 2:** Mechanics derived from identity — stats, abilities with effects using the full effect schema including `behavior` field

The Layer 2 prompt (`character_layer2.json`) explicitly teaches the LLM about all nine behaviors and encourages inventing novel status types.

**Validation** (`_validate_and_fix_mechanics`):
- Enforces weapon/armor consistency (ranged weapon → attack_range ≥ 2, heavy armor → high defense/low speed)
- Ensures all abilities have `description` and `tactical_hint`
- Normalizes effects: strings → dicts, fills missing fields (`target`, `category`, `chance`)
- Calls `ensure_registered(effect)` on every effect — novel types get definition files auto-created

**Fallback:** If both LLM attempts fail, `_default_character()` uses keyword matching against 8 archetype templates (Gunslinger, Mage, Knight, Rogue, Cleric, Berserker, Ranger, Swordmaster) with pre-authored abilities.

---

### 5. How Abilities Resolve in Combat

**Full path for an ABILITY action:**

1. **agent_brain.py** `decide_action()` — builds prompt with ability descriptions, tactical hints, effects, and available abilities visible to the LLM agent
2. **LLM returns** JSON: `{action: "ABILITY", ability_name: "...", target_name: "..."}`
3. **agent_brain.py** `_parse_action()` — finds ability dict on scratch, constructs transient `Ability` dataclass, returns `CombatAction`
4. **battle_server.py** `process_turn()` — checks for `skip_turn` status, delegates to resolver
5. **action_resolver.py** ABILITY handler:
   - Validates target alive + mana sufficient
   - Deducts mana, logs "X uses Y on Z"
   - **Blind check:** scans attacker statuses for `miss_chance` behavior, rolls magnitude as miss probability
   - **Dodge check** (if not blinded): `(target.speed - attacker.speed) × 0.03` chance
   - If neither triggered: calculates damage through `_apply_damage()` (which checks `reduce_outgoing_damage`, `boost_outgoing_damage`, `reduce_incoming_damage` behaviors), then dispatches each effect via `_resolve_effect()`
   - Sets cooldown, marks `has_acted`, appends to `abilities_used` — **regardless** of miss
6. **battle_server.py** — emits combat memories and chat memories
7. **battle_runner.py** — writes movement JSON with updated stats, status effects, abilities

---

### 6. Effect Dispatch (`_resolve_effect`)

Routes by category:

- **movement/teleport** → `_resolve_teleport()` — finds empty adjacent tile near target, moves caster, updates grid
- **heal** → restores HP = magnitude × max_hp on recipient (self or target)
- **buff** (target=self) → applies status dict to caster unconditionally
- **debuff** (target=enemy) → rolls `random.random() < chance`; on success applies to target, on failure logs "X resists Y!"

String effects encountered at runtime are normalized to dicts with intelligent defaults based on type name.

---

### 7. Status Effect Lifecycle

**Applied:** Added to `combatant.scratch.status_effects` as `{type, duration, magnitude, source}`

**Enforced:** At each relevant code point, `get_behavior(effect["type"])` is called to determine mechanical consequence

**Expired:** At end of each round, `clear_expired_status_effects()` decrements durations, removes effects at duration 1

**Displayed:** Frontend receives full dicts `{type, duration, magnitude}` in movement JSON, renders as colored badges with `formatStatusName()` title-casing

---

### 8. End-of-Round Processing

After all combatants have acted, in order:

1. **Bonus action** — speed ≥ 15 → 20% chance of free basic attack on random enemy in range
2. **Cooldown tick** — decrement `current_cd` on all abilities
3. **Damage-over-time tick** — `damage_over_time` behavior deals magnitude × max_hp (can kill)
4. **Mana recovery** — `max(1, int(max_mana × 0.1))` per round, only if alive
5. **Status expiry** — durations decremented, expired effects removed
6. **Flag reset** — `has_moved`, `has_acted` cleared

---

### 9. What the LLM Agent Sees

The decision prompt includes:

- **Abilities block:** Name, damage, range, mana cost, pattern, cooldown status, description ("What it does"), tactical hint ("When to use"), effects with type/duration/magnitude
- **Legal actions block:** Which abilities are READY (off cooldown + affordable), which enemies are in range of each
- **Status effects:** Listed as comma-separated type names on "YOUR STATUS"
- **Defend warning:** If consecutive defends, shows diminishing returns percentage

---

### 10. The Self-Expanding Loop

This is the key architectural achievement: the system is self-expanding without code changes.

1. Operator describes a character concept ("fire mage who immolates enemies")
2. LLM Layer 2 invents themed effects: `immolate` (behavior: `damage_over_time`), `heat_haze` (behavior: `miss_chance`), `flashfire_empower` (behavior: `boost_outgoing_damage`)
3. `ensure_registered()` creates definition JSONs for each novel type
4. During combat, the resolver looks up behaviors from the registry and enforces them
5. The LLM agent sees these effects in its prompt and reasons about them
6. The frontend displays them as formatted badges

No one wrote code for "immolate" or "heat_haze." The LLM invented them, the registry classified them by behavior, and the existing enforcement code handled the rest. The definitions persist on disk for future battles.
